# Design

## Context

See [proposal.md](proposal.md). 現行の `ContentView` は「入力・履歴・ホーム・リマインダー・設定」の5タブで、`AnalyticsView` と `SettingsView` の双方から `FinanceHubView` を開ける。`FinanceHubView` は口座、支払予定、契約、所有物に加えて旧 LifeCost JSON 取込を持ち、`RemindersView` は別系統の旧 LifeCost 予定読込画面にリンクしている。新規ストアには既定カテゴリが作られる。保存は SwiftData v4、家計簿バックアップは JSON v4 で旧版も読める。

## Goals / Non-Goals

**Goals:**

- 5番目のタブを独立した「メニュー」に替え、管理入口と設定への移動を一貫させる。
- 空の利用者データだけに初回作成入口を示し、作成・キャンセル・後で始める操作を途切れさせない。
- 旧 LifeCost の外部読込経路を停止しつつ、既存ストアと家計簿バックアップにある値を保持する。
- この変更の検証と、公開前に別途必要な検証・運用準備を区別する。

**Non-Goals:**

- 旧アプリ移行の新方式を設計・実装すること。
- 保存済みの旧取込履歴を消去すること、SwiftData v4 の既存エンティティを削除すること。
- CloudKit の有効化や App Store 公開作業をこの変更だけで完了すること。

## Decisions

### 1. メニューを第5タブとする

`ContentView` の第5タブを「メニュー」にし、新しいメニュー画面から口座・カード、支払予定、契約、所有物、設定を開く。`SettingsView` は独立タブからメニュー配下の画面へ移す。ホームの集計、残高、期限、予定の表示は残し、契約・所有物の編集を始める重複リンクは外す。代案は設定画面を名称変更する方法だが、利用者が指定した独立した管理メニューにならず、設定と日常の管理操作が混ざるため採らない。タブ数を増やして6タブにする案も、既存の主要画面を押し出すため採らない。

### 2. 初回入口は利用者データと完了状態で判定する

初期カテゴリは自動生成されるため、初回判定から除外する。取引・口座・契約・所有物のいずれかがあれば通常画面を表示する。これらが空で、端末に初回案内完了が記録されていないときだけ作成入口を表示する。後で始める選択は端末設定に記録する。既存データを持つ利用者には入口を割り込ませない。代案の「毎回、空なら案内する」は利用者が後で始める選択を尊重できないため採らない。

初回入口には収支記録、サブスクリプション、所有物、後で始めるを置く。契約・所有物の新規エディタは現在それぞれの画面内で閉じた表示状態を持つため、共通の作成導線として呼び出せるよう画面構成を整理する。保存は既存の Use Case を通し、失敗時はエディタの入力を維持する。新しい保存モデルは導入しない。

### 3. 旧読込は入口と実行経路を停止し、保存表現は残す

`FinanceHubView` の旧 JSON 取込、`RemindersView` の旧予定読込リンク、関連するファイル選択・プレビュー・自動案内と Use Case の読込入口を除く。旧共有ファイルの存在だけでは起動時の処理を行わない。旧 LifeCost のモデル型は保存済み `ImportedPayment`、`FinanceState`、バックアップのデコードに参照されるため、参照が残る範囲の型・依存関係は維持する。不要になった `LifeCostCore` などの依存は参照を確認してから外す。代案の保存モデル・旧形式デコーダまで一括削除する方法は、既存ストアやバックアップを読めなくするおそれがあるため採らない。

家計簿自身の JSON 復元は旧 LifeCost 移行とは区別して維持する。旧版家計簿 JSON の読込互換性も、この変更では縮小しない。

### 4. 製品化課題は後続の受け入れゲートとして管理する

今回のタスクには新しい導線と既存データ保護の自動テスト・ビルド確認を含める。一方、実機 UI、VoiceOver、iPad、通知配信、CloudKit 同期、プライバシー表示、署名・ストア素材は別の受け入れ記録が必要であり、本変更のテスト成功だけで公開可能とは判断しない。製品化候補は proposal の優先順を使用する。

## Risks / Trade-offs

- [旧読込コードに保存形式が依存する] → 型と保存フィールドを先に棚卸しし、旧履歴を含むストアの再起動・JSON 往復を回帰テストする。
- [既存の未処理旧予定を操作する画面がなくなる] → データは保持し、旧移行再設計の後続課題として明示する。通常の支払予定と混同させない。
- [初回入口から契約・所有物を作成できない画面構造] → 新規エディタの呼出しを共有し、メニューからの追加と同じ保存経路を使う。
- [初回案内状態が端末ごとに異なる] → 保存済みデータの存在を優先して案内を抑止し、完了設定は表示制御だけに使う。
- [公開済み利用者の旧取込手段が消える] → 配布前に公開状況を確認し、必要なら後続の移行機能を先行させる。保存済みデータの消去は行わない。

## Migration Plan

1. 現行 v4 ストアと JSON バックアップの例を用意し、旧取込履歴を含む回帰データを固定する。
2. メニューと初回入口を追加し、既存画面の重複リンクを整理する。
3. 旧 LifeCost 読込の UI と実行経路を停止し、参照がなくなった依存のみ外す。保存モデルと家計簿バックアップ互換性は残す。
4. 既存データあり／空データ、再起動、保存失敗、旧履歴を含むストア・バックアップを確認する。端末での画面確認は公開前ゲートへ記録する。
5. 問題があれば、旧データを変換・消去せず、読込経路の変更を戻せるようにする。スキーマ変更を伴わないため、既存ストアの復旧に新たな移行処理を要求しない。
