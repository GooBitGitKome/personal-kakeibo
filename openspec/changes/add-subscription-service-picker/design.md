# Design

## Context

動機と変更範囲はproposal.mdを参照。

確認できた実装:

- `ContractEditorView` は管理画面からの追加・既存契約の編集・初回案内からの追加で共有されている。新規の初期種類はサブスクリプションである。
- 編集中の契約はローカル状態に保持し、金額などは別の入力状態も持っている。現在はサービス候補や料金カタログを持たない。
- 保存は既存の `saveContract` を通す。選択支援のための保存モデル変更は必要ない。

本変更では、名前を入力済みの場合の置き換え、候補一覧からの復帰、既存契約編集との境界を先に決めるため設計書を設ける。

## Goals / Non-Goals

**Goals:** 同じ契約追加画面で候補から名前を入力し、入力中の契約条件を保って保存まで進める。

**Non-Goals:** 料金・プラン・周期の自動入力、サービスとの契約連携、候補のオンライン更新、ロゴの取得、既存契約への候補ID付与。

## Decisions

### 1. 新規契約の基本セクションに選択入口を置く

基本セクションの先頭を「種類」「サービスから選ぶ」（新規かつサブスクリプションの場合だけ）「サービス・契約名」の順とする。名前入力欄は常に使用できる。既存契約の編集では選択入口を出さない。

候補画面は追加画面内の既存NavigationStackにプッシュする。タイトルを「サービスを選ぶ」とし、カテゴリ別の文字一覧と、先頭の「その他・手入力」を表示する。選択後は追加画面へ戻る。14件の初期一覧には検索を追加せず、標準のスクロールで全件に到達できる構成とする。

別のモーダルを重ねる案より、戻る操作と入力状態の保持を同じナビゲーション内で扱える。既存の名前入力欄をなくす案は自由な契約名の登録を妨げるため採用しない。

### 2. 選択画面には名前だけを渡す

選択画面の追加先は `PersonalKakeibo/Presentation/SubscriptionServicePickerView.swift` を想定する。カタログは画面用の不変なローカル定義（識別子・表示名・表示カテゴリ）として分離し、選択画面が変更できる入力は名前のBindingだけにする。契約全体や金額・日付のBindingは渡さない。

外部向けAPIや永続化型は追加しない。候補の識別子は一覧表示のためだけに使い、保存されるのは通常の契約名である。候補一覧の後日の変更・削除は、保存済みの名前に影響させない。

### 3. 入力済みの名前を置き換える前に確認する

- 現在の名前が空欄（空白のみを含む）か、選択候補と完全に同じ場合は、その名前を反映して追加画面へ戻る。
- それ以外は「サービス名を置き換えますか？」と現在の名前・選択した名前を確認表示する。「置き換える」で名前だけを反映して戻り、「キャンセル」で元の入力を保って候補一覧に留まる。
- 「その他・手入力」と一覧の戻る操作では、入力値を変更せず追加画面へ戻る。「その他・手入力」の場合は名前入力欄へフォーカスする。
- 種類をサブスクリプション以外へ変更すると入口を隠す。種類の切り替えや再表示で候補を自動適用せず、入力中の名前を保つ。

確認なしで名前を毎回上書きする案は、手入力したプラン名などを失わせるため採用しない。選択時に金額や周期を初期化する処理も設けない。

### 5. 保存は現在の操作を使う

候補を開く・選ぶ・戻る操作では保存や予定生成を呼ばない。追加画面の「保存」だけが既存Use Caseを実行する。金額未入力などは現在と同じエラーと入力保持の動作を使う。保存失敗時の巻き戻しは既存の保存経路を再利用する。

## Risks / Trade-offs

- [入力済み情報が選択時に消える] → 名前だけのBindingと置き換え確認に加え、金額・周期・カテゴリ・日付・支払元の保持をUIテストする。
- [主要サービスの範囲が利用者と合わない] → 初期14件を提案上の既定値とし、常に手入力を使えるようにする。
- [名称が将来変わる] → 候補をアプリ更新で見直しても、保存済み契約名は通常の文字列として保持する。
- [一覧が狭い端末で使いにくい] → iPhone 12 miniで各カテゴリと手入力への到達、文字サイズ拡大時の読取り、選択後の復帰を確認する。

## Migration Plan

保存モデル・バックアップのバージョン変更は不要。既存契約は現在の編集画面で扱う。導入時には追加画面と同梱カタログを更新し、問題があれば選択入口だけを取り外して既存の手入力へ戻せる。
