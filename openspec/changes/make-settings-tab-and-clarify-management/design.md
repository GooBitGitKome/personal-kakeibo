# Design

## Context

動機はproposal.mdを参照。現在のタブ選択は整数で、通知コールバックは3番のリマインダータブを選ぶだけである。設定は管理画面から開く構造で、初回作成は4番の管理タブを選択している。

## Goals / Non-Goals

**Goals:** タブ順の変更と、通知から管理内の画面へ進む動作を一貫させる。

**Non-Goals:** 保存形式の変更、通知内容や財務計算の変更、未承認の管理ダッシュボード追加。

## Decisions

- 管理は3番、設定は4番のタブとする。初回作成も3番を選択する。
- 管理の移動先を表すHashableな列挙型と、その配列による画面遷移状態をViewModelへ置く。管理の5つの入口を値を持つNavigationLinkへ揃え、ContentViewの管理用NavigationStackで移動先を解決する。
- 通知コールバックは管理タブを選び、遷移配列をリマインダー1件へ置き換える。単にタブだけ選ぶ案では管理一覧で止まるため採用しない。配列への追加では通知のたびに同じ画面が増えるため置き換える。
- 設定から繰り返し収支への重複入口を外す。通知設定と予算設定は今回の導線変更では既存画面を使う。

## Risks / Trade-offs

- [初回作成が設定タブへ戻る] → キャンセル後の管理タブ選択をUIテストする。
- [通知で管理一覧に止まる、同じ画面が重複する] → 設定・契約を開いていた状態と通知の繰り返しをViewModelテストで確認し、UIテストで同じ管理内リマインダーへの移動を確認する。
- [管理の改善範囲が未確定] → 確定済みのタブ変更を進め、追加の名称・説明・表示情報は利用者の選択後に仕様へ反映する。

## Migration Plan

画面遷移状態はメモリ内だけに保持する。ストアやバックアップの移行は不要。問題があればナビゲーション変更のみを戻せる。
