# Proposal

## Why

プロトタイプの最終状態を再現できる Git 上の基準点がなく、既存の開発仕様・設計判断・検証記録を Issue、PR、リリースに結び付ける運用も未整備。分割払いなどの開発を始める前に、どのソースを何で検証し、誰がリリースを判断したかを追跡できるようにする。

## What Changes

- アプリとローカル Swift パッケージを含む現状の差分を棚卸しし、必要なソースをレビュー済み基準コミットとして確定し、そのコミットに `v0.1.0` を付ける。タグはプロトタイプの基準点であり、正式配布や未実施の検証の完了を意味しない。
- Git 管理の対象を整理し、再現に必要なプロジェクト設定・テスト・既存の検証記録は保持する。ビルド生成物、個人の Xcode 状態、署名用秘密情報、私的な家計データは公開対象に含めない。
- Issue → 要件・受け入れ条件 → 設計 → ブランチ・実装 → テスト → PR・レビュー → マージ・リリース → 動作検証・Issue 完了の手順を定める。要件・設計・テスト方針の決定とレビュー・リリースの最終判断は人が担い、AI の主要な提案や生成物は人による評価・修正・検証が追える形で記録する。
- README を入口に既存の仕様・設計・検証資料をつなぎ、ADR と `CHANGELOG.md` を整備する。GitHub Actions で自動テストと署名不要の iOS ビルドを検証する。配布やタグの作成は自動化しない。
- ロードマップは `v0.1.0` プロトタイプ最終版、`v0.2.0` 分割払い、`v0.3.0` ボーナス払い、`v0.4.0` 簡易登録の高速化、`v1.0.0` 品質検証・正式リリースとする。`v0.2.0` 以降の機能仕様と実装、製品の挙動変更、App Store 配布は対象外。

## Capabilities

### New Capabilities

- `repository-release-workflow`: コントリビューターが変更の判断、検証結果、リリース対象コミットを追跡できるリポジトリ運用と自動チェック。

### Modified Capabilities

## Impact

- 対象: Git 管理ルールとリリース参照、README、`CHANGELOG.md`、既存の仕様・検証記録と `docs/decisions/`、`.github/` のテンプレートとワークフロー。
- 検証に使用: `Package.swift`、`Tests/`、`project.yml`、`PersonalKakeibo.xcodeproj`、`LocalPackages/`。アプリの API・保存形式・UI は変更しない。
- GitHub 上での公開、タグの push、正式配布は、それぞれ必要な権限と人による判断を要し、自動では行わない。
