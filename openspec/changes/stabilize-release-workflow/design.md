# Design

## Context

動機と範囲は [proposal.md](proposal.md) を参照。現在の作業ツリーには追跡済みの変更と未追跡ファイルが混在する。`Package.swift` と `project.yml` は `LocalPackages/LifeCostIntegration` を参照し、そのディレクトリは現時点では未追跡。Xcode プロジェクトには追跡済みの `xcuserdata` があり、`.build/` と `.o` も作業ツリーに存在する。README は Xcode 26.3 を開発環境として案内し、`Tests/` と実機確認手順は既にある。`project.yml` にはアプリ、Widget、UI テストのターゲットがある。

## Goals / Non-Goals

**Goals:** Git から復元可能な基準スナップショット、同じ検証手順を開発者と CI が使える構成、既存資料を活かした変更と検証の追跡。

**Non-Goals:** ビルドシステムの置き換え、署名済み成果物の生成・配布、既存履歴の書き換え、アプリの製品仕様の変更。

## Decisions

1. **基準コミットと運用整備を分離する。** 既存 `HEAD` にそのままタグを付けると現在のプロトタイプを取りこぼし、一括コミットすると生成物や別作業まで取り込む。候補の差分と未追跡ソースをパス・必要ならハンク単位で確認し、管理者が承認した内容だけをコミットする。ローカルのファイルは消さず、追跡済み `xcuserdata` は候補の Git 管理対象から外す。生成物・ローカル構成の除外を `.gitignore` に反映する一方、`project.yml`、共有プロジェクト設定、アプリと Widget の再現に必要な `LocalPackages/`・ソース・テストを残す。署名用の秘密情報、私的な家計データ、公開すべきでない画像やログは候補のツリーに入れない。未承認の変更を含めず、公開前に既存履歴も確認する。問題があれば公開を止め、履歴の処置は別判断とする。
2. **検証・承認した SHA にだけ注釈付きタグを打つ。** 候補コミットを清浄な macOS/Xcode 環境にチェックアウトし、パッケージテストと署名不要の Simulator ビルドを実行する。コマンド、ツールチェーン、結果、未検証項目を記録して人が承認した SHA をタグに指定し、参照先を照合する。タグ作成直前にローカルと対象リモートの同名タグを確認し、別 SHA のタグを上書きしない。公開時は対象リポジトリとコミットの公開可否を人が確認したうえで別途 push する。Git タグをアプリ内部のビルド番号とみなさず、現行のアプリ設定は基準タグに合わせて変更しない。
3. **CI はパッケージテストと Simulator ビルドを必須の確認項目にする。** `.github/workflows/ci.yml` を PR と既定ブランチへの push で起動する。対応する Xcode を備えた macOS ランナーを選び、選択した Xcode/Swift の版をログと手順に残す。`swift test` で既存のドメイン・永続化テストを実行し、`project.yml` から XcodeGen で再現した共有 `PersonalKakeibo` スキームを `xcodebuild` の汎用 iOS Simulator 宛てで、署名なしでビルドする。CI と README は同じ入力と手順を使う。UI テストは SpringBoard からの操作を含むため、この段階では CI の合格で UI テストの合格を代替せず、関連シナリオを別途実行・記録する。CI は読み取り権限のみとし、署名資格情報や実データを持たせない。失敗を無視して成功扱いにしない。
4. **資料を二重管理しない。** README はアプリの概要・構成・起動と検証を案内し、`CONTRIBUTING.md`、`CHANGELOG.md` と既存の開発仕様・決定記録・検証記録へリンクする。要件・設計は現行の `docs/development-specification.md` と機能ごとの OpenSpec を参照し、同内容を `docs/requirements/` や `docs/design/` に複製しない。採用理由・比較した選択肢・結果を `docs/decisions/` に ADR として追加し、新たに `docs/adr/` へ分散させない。変更履歴とロードマップは分離し、将来版をリリース済みとして記載しない。
5. **Issue と PR は人の判断を残す入口にする。** Issue テンプレートに背景、目的、機能・非機能要件、受け入れ条件を設け、PR テンプレートに Issue、設計、テスト結果、未検証項目、AI 利用と人のレビューを記載する欄を設ける。Issue へのリンクはマージ時に自動クローズするキーワードではなく通常リンクを使い、受け入れ条件をリリース後に確認してから人が閉じる。AI は課題整理・代替案・テスト設計の補助、共同実装、レビュー指摘を担当し、要件・設計・テスト方針、レビュー、リリースの最終判断を人から移さない。

## Risks / Trade-offs

- 作業ツリーでのみ動き、タグのチェックアウトで壊れる → ローカル Swift パッケージと共有設定を含め、候補 SHA からクリーンに再検証する。
- GitHub のランナー更新で Xcode のパスや版が変わる → 選択した版をログに記録し、利用できない場合は失敗を明示する。本番配布の前提となる実機・CloudKit 検証は既存の手順で別管理する。
- ポートフォリオ公開で個人情報や秘密を公開する → 画像・ログ・未追跡ファイルだけでなく公開される既存履歴も確認する。既に追跡された情報は `.gitignore` では過去履歴から消えない。

## Migration Plan

1. 承認済みのパスだけで基準候補をコミットし、候補 SHA をクリーン環境で検証する。失敗または未検証ならタグを作らず、理由を記録して候補を修正する。
2. 候補 SHA を管理者が承認したら `v0.1.0` を付け、実測結果と既知の制約を変更履歴に記録する。運用資料と CI を基準候補とは別のコミットで追加し、PR と既定ブランチの実行結果を確認する。
3. CI 設定に問題があれば修正または運用側のコミットを取り消す。公開済みのタグが誤っていた場合は移動せず、訂正を記録して次のタグを管理者が決める。
