# リリースと開発プロセスの方針

日付: 2026-11-27

## 背景

プロトタイプの状態を再現できる Git 上の基準点がなく、要件・設計・検証の記録も Issue、PR、リリースと結び付いていなかった。分割払い（v0.2.0）などの開発に入る前に、検証済みの基準点と、判断を追跡できる開発の流れを決める。

## 決定

1. **バージョン**: v0.1.0 を現在のプロトタイプ最終版とし、v0.2.0 分割払い、v0.3.0 ボーナス払い、v0.4.0 簡易登録の高速化、v1.0.0 品質検証・正式リリースの順で進める。
2. **タグ**: 注釈付きタグ `vX.Y.Z` を、クリーンな環境で検証し人が承認したコミットにだけ付ける。公開済みのタグは動かさず、誤りは訂正を記録して次のバージョンで直す。タグは正式配布や、署名・実機・CloudKit の検証済みを意味しない。
3. **開発の流れ**: Issue、要件定義、設計、ブランチ・実装、テスト、PR、レビュー、リリース、動作検証・Issue 完了の順に進める。詳細は [開発ガイド](../../CONTRIBUTING.md)。
4. **役割**: 課題の発見、要件定義、アーキテクチャ設計、テスト設計、リリース判断は人が主担当。AI は補助、レビュー、代替案の提示を担当し、実装は共同で行う。コードレビューの最終判断は人が行い、AI は問題点を指摘する。AI の関与は PR に記録する。
5. **資料の置き場**: 要件・設計は既存の [開発仕様](../development-specification.md) と OpenSpec の変更に置き、決定の記録はこの `docs/decisions/` に ADR として置く。
6. **CI**: GitHub Actions でパッケージテストと署名なしの iOS Simulator ビルドを実行する。タグの作成と配布は自動化しない。

## 検討した代替案

| 案 | 採用しなかった理由 |
|---|---|
| `docs/requirements/`、`docs/design/`、`docs/adr/` を新設する | 既存の開発仕様、OpenSpec、`docs/decisions/` と内容が重複し、二重管理になる |
| 現在の `HEAD` にそのままタグを付ける | 未コミットだった Widget・統合家計簿・テストが基準点に入らない |
| 作業ツリーを検証せずに一括コミットしてタグを付ける | ビルド生成物や個人の Xcode 状態が混ざり、基準点を再現できるか分からない |
| PR のマージで Issue を自動クローズする | 受け入れ条件をリリース後に確認する前に Issue が閉じる |
| UI テストも CI の必須チェックにする | UI テストはホーム画面や Widget の操作を含み、この段階では CI の結果で代替できない。Simulator での実行と記録は別に行う |
| 全工程を AI に任せる | 要件・設計・リリースの判断の根拠が残らず、品質を人が保証したことを示せない |

## 結果

- v0.1.0 は検証した範囲だけを示す基準点になる。検証内容は [検証記録](../validation.md)、変更は [CHANGELOG](../../CHANGELOG.md) に残る。
- 機能ごとの判断が Issue、OpenSpec、PR、ADR からたどれる。
- 実機・iCloud・VoiceOver・UI テストは CI の対象外で、引き続き手動で確認する。
- Apple の Team ID は公開済みの履歴（`origin/main`）に含まれ、書き換えは行わない。端末名は `docs/validation.md` の未 push のコミットに含まれる。いずれも公開前の整理は別の変更で扱う。
